# FPVRaceOne timing test rig

Measures whether the lap timer is **late** or **inconsistent**, using a
deterministic synthetic stimulus instead of a real drone.

Real-world stimulus can't answer this. A servo swinging past an antenna has
millisecond-scale variance of its own, so you end up characterising the servo.
This rig replaces the RX5808's analog RSSI output with a precisely-timed
envelope generated by a second ESP32.

## What it measures

| Metric | Meaning | How |
|---|---|---|
| **Bias** | Is the timer systematically late? | mean(reported lap − known interval) |
| **Jitter** | Is the timer inconsistent? | stdev of that error |
| **Latency** | Absolute stimulus→detection delay | marker GPIO, timed on the emulator |
| **Min pass width** | Fastest detectable gate pass | duration sweep |

### Why no clock synchronisation is needed

A lap time is a **difference measured entirely by FPVRaceOne's own clock**. The
emulator generates pulses exactly *T* apart; the device reports lap time *L*;
the error is `L − T`. No relationship between the two clocks is involved, so USB
latency and jitter are irrelevant.

Absolute latency works the same way — the emulator timestamps both its own
stimulus and the device's marker edge on one hardware timer.

## Hardware

- **Emulator**: ESP32-WROOM-32. Chosen because it is the only ESP32 variant with
  a built-in DAC — the C6, C3 and S3 have none. 8-bit also matches `readRssi()`'s
  own quantisation exactly.
- **DUT**: the XIAO ESP32-C6 FPVRaceOne unit.

## Wiring

```
ESP32 WROOM-32 (emulator)              XIAO ESP32-C6 (FPVRaceOne)

  GPIO25 / DAC1  ──[2.2k]──┬────────── A2  = GPIO2   PIN_RX5808_RSSI
  (header pin 9)           │
                         [1.0k]
                           │
  GND (pin 14/32/38) ──────┴────────── GND           common ground, REQUIRED

  GPIO4 (pin 26, input) ◄───────────── D3  = GPIO21  PIN_TIMING_MARKER
```

The divider drops the DAC's 0–3.3 V to ~1.03 V, matching the RX5808's 0–1 V
output and landing full scale near `RSSI_SCALE_MAX` (2400 counts ≈ 1.026 V under
`ADC_6db`). Keep 2.2k/1.0k rather than scaling up — it holds source impedance at
~690 Ω for clean ADC sampling.

**Disconnect the real RX5808 from the RSSI line only.** Two sources fighting
invalidates everything. The three SPI lines can stay wired — the emulator is
analog-only and ignores them.

> Note: the XIAO C6 block in `lib/CONFIG/config.h` uses **Arduino aliases, not raw
> GPIO numbers**. `PIN_RX5808_RSSI` is `A2` = GPIO2. Don't take the pin numbers
> from the ESP32C3 block above it.

## Build and flash

**1. FPVRaceOne** — set the marker on in `lib/CONFIG/config.h`:

```c
#define TIMING_MARKER_ENABLED 1
```

Then `pio run -t upload`. Remember to set it back to `0` before releasing —
without it the pin is never driven and the whole feature compiles away.

**2. Emulator** — from the main project's PlatformIO task list:

> **Upload RX5808 Emulator (Test Rig)**

or from a terminal:

```
pio run -t upload_emulator
```

The task picks the port by USB vendor ID and **refuses to upload to a
FPVRaceOne unit**: the WROOM-32 devkit presents a CP210x/CH340/FTDI bridge,
while the XIAO C6 presents Espressif native USB (0x303A). Set `EMULATOR_PORT`
to force a port if the heuristic guesses wrong.

## Running — GUI (recommended)

```
python tools/timing-harness/gui.py
```

Buttons for the three tests in the order you should run them, editable stimulus
settings, auto-detected ports, and plain-language interpretation of every
result. Tkinter only, so no install beyond pyserial.

## Running — command line

```bash
python harness.py --list                       # find the two ports

# Validate the analog path BEFORE trusting any timing number
python harness.py --emu COM7 --dut COM5 level --value 200

# Accuracy + consistency
python harness.py --emu COM7 --dut COM5 interval --count 50 --interval 3000

# Minimum detectable pass width
python harness.py --emu COM7 --dut COM5 sweep --widths 100,80,60,40,30,20,15,10
```

The GUI imports its measurement logic from `harness.py`, so the two cannot
drift apart.

### Suggested sequence

1. `level` — confirm the device's RSSI tracks the commanded DC value. This
   validates the divider before any timing is measured.
2. `interval` in **polled** mode — record bias, stdev, latency.
3. Switch Settings → Signal Processing → Sampling mode → **DMA continuous**,
   reboot, **re-run the calibration wizard** (peak-hold changes what the numbers
   mean, so old thresholds don't carry over), then repeat.
4. `sweep` in both modes — this is where DMA peak-hold should separate from
   polled, if it does at all.
5. Cross-check against Diagnostics → RSSI Sample Timing and CPU Load from the
   same runs, so bench and on-device instrumentation corroborate each other.

## Gotcha: Min Lap silently discards passes

Lap detection is gated by **Min Lap** (default **5000 ms**). Any crossing sooner
than that after the previous one is discarded *by design*. Gate 1 is exempt.

So a run whose pass interval is shorter than Min Lap reports **exactly one lap**
and looks like total detection failure, when the firmware is behaving perfectly:

```
Passes generated : 30
Laps reported    : 1        <- every pass after Gate 1 hit the minLap guard
```

Both tools now read the device's Min Lap over USB and refuse to run rather than
produce that misleading result. Three ways forward:

- Keep the default 6000 ms interval (above the 5000 ms Min Lap).
- Set Min Lap to 0 in Settings — allows much shorter intervals.
- Tick **Force device Min Lap = 0** in the GUI, which sets it for the run and
  restores it afterwards. This turns a ~16 minute sweep into about 4.

## A note on reading amplitude from the Calibration chart

Don't. The chart streams RSSI at 10 Hz (one sample per 100 ms), so a 40 ms pass
is usually sampled on its rising or falling edge, not at the peak — the trace
under-reports amplitude badly for short pulses.

Use **Check Analog Path** instead. It holds steady DC levels for ~800 ms each,
which the 10 Hz stream resolves properly, and fits the gain across eight points.

## Interpreting results

**Bias** largely cancels for lap times — the same delay applies to both
crossings and subtracts out. A large bias matters mainly for head-to-head racing
between two *different* devices, where the delays may differ.

**Jitter is the one that costs you.** Lap-time error is
`jitter(crossing 2) − jitter(crossing 1)`, so consistency is what shows up in the
recorded lap.

**Detection rate in the sweep** is the quantitative form of "how fast a drone
can we detect". If polled and DMA converge here, DMA is not earning its
complexity.

## Limitations

This reproduces the RSSI **envelope**, not RF. No multipath, no antenna nulls, no
interference. It faithfully exercises the acquisition and detection pipeline; it
does **not** predict real-world detection reliability. Worth stating plainly so
the results aren't over-claimed.

The first lap of each run is discarded — FPVRaceOne's first crossing is Gate 1,
which *starts* a lap rather than completing one, so its reported time is not an
inter-pulse interval.
